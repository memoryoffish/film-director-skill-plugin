# refsound

你听不了声音。挑录音时靠两样东西代替试听：听过的人留下的信号，和你自己可以量出来的数。

脚本在本目录的 `scripts/refsound.py`，下面记作 `$R`。本目录是 film-director skill 里的 `refsound/` 子文件夹，脚本是 `<film-director 的目录>/refsound/scripts/refsound.py`。

选材的四条基本规则出自 [vibe-motion/sound](https://github.com/vibe-motion/sound)（B 站「浙大猫学长」）。这里只借用规则，代码是另写的；规则 5～14 是在二十来种声音、两千多条候选上实测后加的。向用户交付时写明这个出处。

## 流程

1. **写 spec**（一个 JSON，放在用户的工作目录里；例子见本目录的 `examples/sounds.json`）。每种声音一项：

   ```json
   {"pages": 4, "keep": 16, "n": 12, "per_user": 3, "licenses": ["cc0", "by"],
    "sounds": {"door_slam": {
      "note": "摔门",
      "queries": ["door slam", "door slamming"],
      "must": [["door"], ["slam", "slamming", "slams", "slammed"]],
      "reject": ["car", "locker", "cabinet"],
      "dur": [0.3, 15],
      "kind": "event",
      "skip": ["lowfreq"]}}}
   ```

   - `queries`：英文搜索词，同一种声音写 2～4 个说法。
   - `must`：每组词里至少要出现一个。**第一组是声源词，必须在标题或标签里**；其余各组出现在标题、标签或描述里都行。匹配时也认加了 s、es、ed、ing 的词尾（`owl` 也认 `owls`，`bark` 也认 `barking`），别的变形要自己列出来（`rainy`、`slamming`）；长词的开头和它一样也不算匹配，`cork` 不认 `corkscrew`。
   - `reject`：只要出现就不要这条录音的词（别的声源、混进录音里的别的东西）。这些词只认原形和复数。
   - `dur`：要的时长范围（秒）。`kind`：`continuous` 是持续的声音，`event` 是一下一下的声音。
   - `skip`：对这种声音跳过哪些检查。`ambient`：它本来就是环境声；`lowfreq`：它本来就低频（雷、洗衣机、摔门）；`tail`：它的余响本来就长（雷）；`synth`：要的就是合成或设计出来的声音（界面音效）；`lowfi`：不介意手机录的或用嘴模仿的。
   - 开头几项对所有声音都适用：`pages` 每个查询词最多翻几页搜索结果，`keep` 过了文字筛选、排好序后下载前几条的预览，`n` 量完声音后每种声音最后取几条，`per_user` 同一个上传者每种声音最多取几条，`licenses` 收哪些许可（只认 `cc0`、`by`）。只要一条音效时把 `n` 写成 1～3；要参考集时用默认的 12。

2. **搜和筛**（只用 Python 标准库，机器要能访问 freesound.org）：

   ```bash
   R=<film-director 的目录>/refsound/scripts/refsound.py
   python3 $R search <spec.json> <输出目录> [--exclude 已用过的编号.json ...]
   ```

   脚本抓 Freesound 的公开搜索页，按规则筛选、排序，下载排在前面那些录音的 MP3 预览。全部候选连同被筛掉的原因都写在 `candidates.json` 里。
   改了 spec 或规则以后，再跑一次并加上 `--revet`：这样不重新搜索，用已有的候选重新筛、排，只给新排进前面的录音补下载预览。排除过的编号会记在候选里，所以 `--revet` 时即使不带 `--exclude`，它们也不会被放回来。

3. **量声音**（要 ffmpeg 与 numpy）：

   ```bash
   python3 $R check <spec.json> <输出目录>
   ```

   解码每条预览，量时长、削波、活动比例、尾巴（从最后一个比最响的帧低不超过 25 dB 的帧往后、到结尾的那段）、各频段能量占比，定最后的清单 `selection.json`，汇总表 `TABLE.md`。

4. **汇报**。推荐哪条录音，就按这个格式报出它的数：`编号 ↓下载量 ★评分(人数)`。下载量排在前面却没有取的，说明为什么没取（原因是 `candidates.json` 里每条的 `rejected`）。CC-BY 的录音给出署名（`selection.json` 里每条的 `credit`）。用户想自己听时，给出那条的 `url`。

## 规则

出自 vibe-motion/sound 的四条：

1. 下载量优先。评分人数比平均分更可信：★4.4(380) 强过 ★4.9(6)。
2. 上传者的描述是最接近试听的信号。描述要明说录的就是这种声源；写了录音设备的更靠得住；手机或内置话筒录的、用嘴模仿的、合成或处理过的不要。描述里的声源和要的不符就不要，下载量再高也不要。
3. 流行不等于合适。先看时长，再量能量落在哪里、尾巴多长，这些都看过之后，才信排在前面的录音。
4. 许可只取 CC0 与 CC-BY。

实测后加的（括号里是实测时见到的例子）：

5. **描述说「像」或「不是」这种声音的不要。** 「could be」「sounds like」「similar to」后面几个词之内跟着声源词，或者「not」「isn't」「no」「never」「without」和声源词之间最多隔两个 a、an、the、really、actually、real、actual，说明录的是别的东西；写了 fake、simulated、artificial 的也不要。（查 cork pop，下载量第一的那条有 62489 次下载、381 人评 4.4，描述是「made with my lips, could be a cork」。另有抖锌板当雷声、揉枕头当篝火的。）只说用途、后面没有声源词的不算（「could be used for a cozy scene」「perfect for movies」）。
6. **声源词必须在标题或标签里。** 只在描述里顺带提到的不算。（查 owl hoot，下载量第一的是 `eerie_forest.mp3`，一段 7 分钟的森林环境声。）
7. **下载量按上传了几年来折算。** 老录音攒下载量的时间长。排序分 = log10(下载量) + 0.5·log10(每年下载量) + 0.3·(评分 − 3.9)，这里的评分按下一条折算；写了录音设备的再加 0.15。
8. **评分折算成一个数。** 用贝叶斯平均 (n·R + 10·3.9) / (n + 10) 折算，n 是评分人数，R 是平均分；评分人数少的，折算出来的数往 3.9 靠。
9. **评分的人不少而分低，直接不要。** 门槛是 5 人以上评分、平均分低于 3.0。（摔门 266440：下载 1345 次，56 人评，平均 1.8。）
10. **描述说是手机录的，但评分的人多、分也高，留下。** 30 人以上评分、平均 4.3 分以上时，听过的人的判断比描述的字面更可信。（猫头鹰 465697：170 人评 4.7。）描述里同时说了是用嘴模仿的，不适用这一条。描述里写了录音机型号时，「internal mics」说的是录音机自带的话筒，不算低保真。
11. **要的不是环境声时，描述里有环境录音或人群一类词的不要。** 较长的环境词和别的词连写在一起也认得出。（手风琴里取用过一条 `Folkfestival (indoors).wav`，它是民俗节的现场录音，内容前后不一样。）
12. **同一个上传者每种声音最多取 3 条。** 免得同一个人传的一整包相似录音占满名额。
13. **量声音的规则按声音的种类定。** 持续的声音看活动比例：把录音切成 0.1 s 一帧，比最响的帧低不超过 30 dB 的帧，占比要 ≥ 0.6。一下一下的声音看尾巴：尾巴超过全长的 60% 而且长于 1 s 才不要，所以很短的片段等于不查。100 Hz 以下的能量超过八成的，算作风噪或手持噪声，不要；本来就低频的声音不查这一项。削波超过 1% 的不要。
14. **每条取舍都留原因，记下抓取日期。** 下载量、评分这些流行度，都是抓取那一刻的数。

做参考集时另外还有两条：

- **不拿被评测的模型来挑。** 如果之后要用某个检测器或嵌入模型来评这批录音，挑录音时就不能用这个模型，否则评出来的结果偏乐观。
- **不与已经用过的录音重叠。** 用 `--exclude` 给出已用的 Freesound 编号：每个文件写成编号的 JSON 列表，或者 `{编号: 原因}` 这样的 JSON 对象，可以一次给几个文件。FSD50K、ESC-50 等数据集的录音也来自 Freesound，要一并排除。

## 局限

- 按文字定的规则会误筛（标题写成 `WashingMachine.wav`，词之间没有空格，就匹配不上）。规则的取向是宁缺毋滥。筛掉的太多时，看 `candidates.json` 里的原因，改了 spec 以后用 `--revet` 重新筛。
- 取的是 Freesound 的 MP3 预览，不是原始文件。要原始文件，得登录 Freesound 以后下载。
- 同一段录音换了一个编号重新上传，这种情况查不出来。
- 脚本解析的是公开搜索页上的结果卡片。一条都搜不到时，先怀疑页面结构变了、`parse` 认不出结果卡片。
- 本 skill 不改本机的网络配置。访问不了 freesound.org 时，由用户自己设 `https_proxy`。
- 这些信号只能替代你没法做的试听，不能替代人亲耳听。用途重要的，最后要让人听一遍。

## 验证

- `python3 -m pytest <film-director 的目录>/refsound/tests`：除了规则 12、14，每条规则都配了例子；规则 5、6、9、10、11 的例子是带编号的真实卡片。
- `examples/sounds.json` 是 8 种常见声音的 spec 例子。这套规则在十几种常见生活声音上试过：只按下载量、每种取前三名的话，约三分之二会被这些规则筛掉（声源不符、时长不对、和已用过的录音或 FSD50K 重叠）。
